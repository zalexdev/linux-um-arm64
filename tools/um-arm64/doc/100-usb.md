# A real USB device in the guest

The guest gets a physical USB WiFi adapter -- a Realtek RTL8811AU, `2357:011f`,
plugged into the phone's OTG port -- bound by the in-tree `rtw88_8821au` driver,
producing a `wlan0` that mac80211 owns.

Status: the kernel side builds, the guest side is written, and the design below
is complete. **Nothing here has been run against the adapter yet.** No URB has
crossed the link; every "should" in this document is a claim about code that has
been read, not about behaviour that has been observed.

## Why this cannot be a normal passthrough

| route | needs | on an unrooted phone |
| --- | --- | --- |
| a real host controller in the guest | PCI, MMIO, an IRQ | UML has no bus at all |
| VFIO | root, an IOMMU, `/dev/vfio` | no |
| `/dev/bus/usb/BBB/DDD` from the app | read/write on the usbfs node | no: the nodes are root-owned and `untrusted_app` has no SELinux rule for them |
| **`UsbManager` + USB/IP** | **a permission dialog the user taps** | **yes** |

The last row is the entire trick, and it is not ours: it is how libusb works on
Android. An app may not open usbfs, but it may ask the user for permission to a
specific device and then receive an **already-open usbfs descriptor** from
`UsbDeviceConnection.getFileDescriptor()`. Every `USBDEVFS_*` ioctl works on that
descriptor -- which is exactly what `libusb_wrap_sys_device()` exists for.

So the adapter is driven from userspace on the Android side, and reaches the
guest as USB/IP: a protocol whose whole purpose is to carry URBs over a socket,
and whose client half (`vhci-hcd`) is already in the kernel.

## The pieces

```
  Android app                        |            guest (UML)
                                     |
  UsbManager.requestPermission       |          rtw88_8821au
    -> openDevice()                  |               |
    -> getFileDescriptor()/detachFd()|            usbcore
            |  fd N                  |               |
          umusb  <=== USB/IP PDUs ===+===>       vhci-hcd
   USBDEVFS_SUBMITURB / REAPURB      |          "port sockfd devid speed"
            |                        |           -> .../vhci_hcd.0/attach
          usbfs                      |               ^
            |                        |          socket opened *in the guest*,
      the real RTL8811AU             |          out through vec0 -> passt ->
                                     |          the phone's loopback
```

### The socket is a guest descriptor, not a host one

This is the one thing that is easy to get backwards. `attach_store()` in
`drivers/usb/usbip/vhci_sysfs.c` does:

```c
	socket = sockfd_lookup(sockfd, &err);
```

`sockfd_lookup()` looks the number up in **the calling process's** file table --
a guest process's table. A descriptor that the UML process inherited on the
Android side has no meaning inside the guest; the number would either be invalid
or, worse, name some unrelated guest socket. UML has no mechanism for injecting a
host descriptor into the guest's table either: `con=fd:N` turns a host descriptor
into a guest *tty*, and vhci rejects anything that is not `SOCK_STREAM`.

So the connection is made from inside the guest, over the network that already
exists (doc/90-networking.md): the guest connects to `10.0.2.2:3240`, passt maps
the guest's default gateway to the host's loopback (`--map-host-loopback`
defaults to the gateway address, and umnet does not pass `--no-map-gw`), and the
connection lands on umusb listening on `127.0.0.1:3240` on the phone. Nothing
binds a UNIX socket -- SELinux denies that under `/data/local/tmp` anyway -- and
nothing needs a privilege.

That means USB traffic and ordinary guest network traffic share one userspace TCP
stack. It is circular but not a loop: the USB/IP connection terminates on the
phone and never leaves it.

### How the fd travels on the Android side

1. The app finds the device (`UsbManager.getDeviceList()`, or an
   `ACTION_USB_DEVICE_ATTACHED` intent filter) and calls `requestPermission()`
   with a `PendingIntent`. The user taps *OK*. The grant is per-device and does
   not outlive an unplug; the intent-filter route, with a `device_filter.xml`
   naming `2357:011f`, is the one that offers the user a "use by default"
   checkbox and launches the app on plug-in.
2. `openDevice(dev)` returns a `UsbDeviceConnection`;
   `getFileDescriptor()` is the usbfs descriptor the framework opened.
   `detachFd()` hands ownership over, so the connection object no longer closes
   it out from under the helper.
3. The number is passed to umusb on its command line, with `FD_CLOEXEC` cleared
   first -- the same shape as umnet handing UML the vector descriptor
   (`harness/umnet.c`), and for the same reason: a descriptor that does not
   survive `exec` is not a descriptor the child has.
4. umusb runs from `nativeLibraryDir` as `libumusb.so`, because that is the only
   directory an app may execute from (doc/70-android.md).

## What umusb has to do

The USB/IP wire format is 48-byte big-endian PDU headers
(`struct usbip_header`, `drivers/usb/usbip/usbip_common.h`) followed by payload:

| PDU | value | meaning |
| --- | --- | --- |
| `USBIP_CMD_SUBMIT` | 1 | one URB, guest -> server |
| `USBIP_CMD_UNLINK` | 2 | cancel a pending URB |
| `USBIP_RET_SUBMIT` | 3 | completion, server -> guest |
| `USBIP_RET_UNLINK` | 4 | cancellation result |

Notes that come from reading the two ends, and that shape the helper:

* **No import handshake.** The normal `usbip attach` sequence has userspace do
  `OP_REQ_IMPORT`/`OP_REP_IMPORT` (version `0x0111`) before handing the socket to
  the kernel; the kernel starts at `USBIP_CMD_SUBMIT` and never sees the
  handshake. Here the guest side is a shell script, which cannot speak a binary
  handshake, and there is exactly one device -- so umusb goes straight to URB
  mode on `accept()`. Nothing in `vhci_hcd` requires otherwise.
* **`devid` and `speed` are agreed, not negotiated.** usbip's convention is
  `devid = (busnum << 16) | devnum`; with one device it only has to match on both
  ends. The guest cannot discover the device's speed before it is attached, so
  the launcher passes it on the kernel command line (`umarm.usbspeed=high`,
  `umarm.usbdevid=...`), the same way `umarm.share=` already tells the guest
  where the host share is.
* **Four control requests must not be forwarded.** The in-kernel USB/IP server
  intercepts them (`tweak_special_requests()`, `drivers/usb/usbip/stub_rx.c`):
  `CLEAR_FEATURE(ENDPOINT_HALT)`, `SET_INTERFACE`, `SET_CONFIGURATION`, and a
  hub-port `SET_FEATURE(PORT_RESET)`. Sent down usbfs as raw control transfers
  they would change the device without the host kernel knowing, so umusb turns
  them into `USBDEVFS_CLEAR_HALT`, `USBDEVFS_SETINTERFACE`,
  `USBDEVFS_SETCONFIGURATION` and `USBDEVFS_RESET`.
* **Claim the interface first.** usbfs auto-claims on first use with a warning;
  claiming explicitly (`USBDEVFS_CLAIMINTERFACE`, or `USBDEVFS_DISCONNECT_CLAIM`
  if some host driver already holds it) is the honest version. The adapter's
  interface is class/subclass/protocol `0xff`, so nothing generic on the Android
  side should be holding it.
* **Several URBs have to be in flight at once.** rtw88 keeps
  `RTW_USB_RXCB_NUM` = 4 bulk-IN URBs outstanding, each of
  `RTW_USB_MAX_RECVBUF_SZ` = 32768 bytes, and aggregates TX into buffers of up to
  `RTW_USB_MAX_XMITBUF_SZ` = 20480 bytes (`drivers/net/wireless/realtek/rtw88/usb.h`).
  A strictly serial submit-then-reap loop would stall the driver; usbfs is built
  for this, since `USBDEVFS_SUBMITURB` is asynchronous and completions are
  collected with `USBDEVFS_REAPURB` / `REAPURBNDELAY` after `poll()` on the
  descriptor.
* **usbfs caps in-flight buffers at 16 MB** (`usbfs_memory_mb`, `devio.c`), which
  is far above anything rtw88 asks for, and is not adjustable from an app anyway.

## The guest side

`vhci-hcd` presents a root hub with `CONFIG_USBIP_VHCI_HC_PORTS` (default 8)
high-speed ports and 8 super-speed ports. Attaching is one sysfs write:

```
	echo "port sockfd devid speed" > /sys/devices/platform/vhci_hcd.0/attach
```

parsed by `sscanf(buf, "%u %u %u %u", ...)`. Two rules come straight from the
source and are worth stating, because getting either wrong fails quietly:

* **The port must match the speed.** `attach_store()` computes
  `rhport = port % VHCI_HC_PORTS` and then chooses the high-speed or super-speed
  hub from the *speed* argument alone. Write a super-speed port number with
  `speed=3` and the device silently lands on high-speed port `port % 8` instead,
  after which the `status` table disagrees with what was asked for. Ports 0-7 are
  the `hs` hub, 8-15 the `ss` hub, and `status` says which is which.
* **The port must be free.** `sta` in the `status` table is
  `enum usbip_device_status`: 4 = `VDEV_ST_NULL` (free), 5 = `VDEV_ST_NOTASSIGNED`
  (socket accepted, device not enumerated yet), 6 = `VDEV_ST_USED`, 7 =
  `VDEV_ST_ERROR`. A busy port returns `-EBUSY`.

`dist/umdebian/usb-attach.sh` does all of that, and reports at each step instead
of failing mute:

```
	exec 7<>/dev/tcp/10.0.2.2/3240
	./usb-attach.sh 7			# or: ./usb-attach.sh --connect 10.0.2.2:3240
```

It refuses a descriptor that is not open in its own shell (vhci would look up
somebody else's), refuses one that is not a socket, refuses a TCP socket that is
not `ESTABLISHED` (which otherwise looks exactly like a device that will not
enumerate), picks a free port on the hub matching the speed, writes the attach
line as a bash builtin redirection so the descriptor is in the writing process's
table, and then waits: first for a `local_busid` to appear in `status`, then for
a driver on the interface, then for a `phy80211` netdev. Every failure names
what it was waiting for and prints the matching kernel messages. The kernel holds
its own reference to the socket once the attach succeeds, so the script can exit
without taking the device down.

## Kernel configuration

`config/usb-wifi.config`, applied to `make ARCH=um SUBARCH=arm64 defconfig`.
Thirteen lines; `olddefconfig` turns them into 92 symbols:

```
	CONFIG_UML_IOMEM_EMULATION=y  CONFIG_UML_DMA_EMULATION=y
	CONFIG_USB_SUPPORT=y  CONFIG_USB=y
	CONFIG_USBIP_CORE=y  CONFIG_USBIP_VHCI_HCD=y
	CONFIG_CFG80211=y  CONFIG_MAC80211=y
	CONFIG_WLAN=y  CONFIG_WLAN_VENDOR_REALTEK=y
	CONFIG_RTW88=y  CONFIG_RTW88_USB=y  CONFIG_RTW88_8821AU=y
```

The first two exist because usbcore depends on `HAS_IOMEM` and `HAS_DMA`, which
UML reached only through `UML_PCI` until `7a70d4a6f` gave each emulation its own
prompt -- and `UML_PCI` on a kernel with no virtio device ID warns at boot with a
stack trace. `vhci_hcd.c` itself contains no MMIO and no DMA; its bus is a
socket.

Everything is `=y`: `CONFIG_MODULES` is not set in the UML defconfig and the
guest image has no modutils.

Verified, `ARCH=um SUBARCH=arm64 LLVM=1`, at `7a70d4a6f`:

| | defconfig | + usb-wifi.config |
| --- | --- | --- |
| build | ok | ok |
| `linux` (unstripped) | 77.4 MB | 100.3 MB |
| clang warnings | 17 | 820 |

The extra 803 are all one warning, `-Wnull-pointer-arithmetic` from
`include/asm-generic/io.h`, where `PCI_IOBASE` is `((void __iomem *)0)` and every
`readb`/`writel` does `PCI_IOBASE + addr`. They arrive with the IOMEM emulation
-- without `HAS_IOMEM` those accessors are not compiled at all -- and they are
noise from generic code that UML now includes, not from anything in this design.
Worth knowing before someone greps a build log for `warning:` and panics.

Not booted. The kernel that boots with USB was built and tested by the main
session; this is a build check of the fragment, nothing more.

## Firmware

`rtw8821a_hw_spec.fw_name` is **`rtw88/rtw8821a_fw.bin`**
(`drivers/net/wireless/realtek/rtw88/rtw8821a.c`, also its only
`MODULE_FIRMWARE`). There is no separate wowlan firmware for this chip.

**When it is needed is not when the driver binds.** `rtw_load_firmware()` uses
`request_firmware_nowait()`, and the wait happens in `rtw_power_on()` ->
`rtw_wait_firmware_completion()` -- which runs when the interface is brought up.
So a missing file gives a `wlan0` that exists and cannot be brought up, with
`Direct firmware load for rtw88/rtw8821a_fw.bin failed with error -2` in dmesg,
rather than a device nothing binds. `usb-attach.sh` says so at that step.

Where to get it:

| release | `firmware-realtek` | ships `rtw88/rtw8821a_fw.bin` |
| --- | --- | --- |
| bookworm (the shipped image) | 20230210-5 | **no** -- it has `rtw8821c`, not `rtw8821a` |
| trixie | 20250410-2 | yes, `/usr/lib/firmware/rtw88/rtw8821a_fw.bin`, 31898 bytes |

Checked against the `non-free-firmware/Contents-all.gz` indices and by unpacking
the trixie `.deb`. The 8821a firmware is recent enough that bookworm's snapshot
of linux-firmware predates it, which is easy to miss: `firmware-realtek` is
installed, the `rtw88/` directory exists, and the one file needed is not in it.

Three ways to get it into the guest, in increasing order of effort:

1. **Copy the one file.** It is 31 KB and has no dependencies on the rest of the
   package:

   ```
	dpkg-deb --fsys-tarfile firmware-realtek_20250410-2_all.deb |
		tar -xO ./usr/lib/firmware/rtw88/rtw8821a_fw.bin \
		> /lib/firmware/rtw88/rtw8821a_fw.bin
   ```

   The same file is in linux-firmware.git under `rtw88/`. Bookworm is usr-merged
   (`/lib` -> `/usr/lib`), so either path works.
2. **Install the trixie package.** It is `Architecture: all` with no `Depends`,
   so `dpkg -i firmware-realtek_20250410-2_all.deb` on bookworm is safe; it is
   only data files.
3. **Build it into the kernel**, with `CONFIG_EXTRA_FIRMWARE="rtw88/rtw8821a_fw.bin"`
   and `CONFIG_EXTRA_FIRMWARE_DIR` pointing at a directory that has it. Tempting
   here, because the kernel ships inside the APK while the Debian image is a
   separate 1.4 GB file -- the firmware then travels with the thing that needs it
   and there is nothing to install in the guest at all. The cost is a kernel that
   carries a licence-restricted blob, so it is a packaging decision rather than a
   technical one.

Two more things the image does not have and will want:

* **`iw` and `wpasupplicant`** (Debian main). The shipped image has `iproute2`
  and nothing else wireless: `wlan0` can be brought up but not associated.
* **`wireless-regdb`** (Debian main), which provides `/lib/firmware/regulatory.db`
  and its `.p7s` signature through `update-alternatives`. The resulting config has
  `CFG80211_REQUIRE_SIGNED_REGDB=y`, so without it cfg80211 keeps its built-in
  world regulatory domain: conservative channel and power limits, but usable.

## How to test it

Nothing below has been run yet; this is the intended sequence.

1. Build a kernel with the fragment, and put it in the APK (or beside `deb`).
2. Get `usb-attach.sh` into the guest. The quickest way needs no image rebuild:
   push it into the launcher's `share/` directory, which the guest mounts as
   `/host`.
3. Plug the adapter into the phone's OTG port. The permission dialog appears
   the moment the app asks; grant it.
4. Start umusb (the app does this) and confirm it is listening:
   `127.0.0.1:3240` on the phone.
5. Boot the guest **with networking on** -- the USB/IP socket rides the same
   passt link, so `UMDEB_NET=0` means no USB either.
6. In the guest:

   ```
	bash /host/usb-attach.sh --connect 10.0.2.2:3240
   ```

   What it should print, in order: the connection, the port it chose, the busid
   the device enumerated as, `2357:011f`, the interface bound to
   `rtw88_8821au`, a `wlan0` on `phy0`, and `wlan0 is up`.
7. Then the ordinary wireless sequence: `iw dev wlan0 scan`,
   `wpa_supplicant -B -i wlan0 -c /etc/wpa_supplicant.conf`, and an address.

Useful views while it fails:

```
	cat /sys/devices/platform/vhci_hcd.0/status	# port state and busid
	ls /sys/bus/usb/devices/			# what enumerated
	dmesg | grep -iE 'usb|vhci|rtw88|firmware'
```

Turn on `CONFIG_USBIP_DEBUG` to see every URB vhci sends, and `CONFIG_RTW88_DEBUG`
for `rtw_dbg()` output through the firmware download; both are left off in the
fragment because they are pure noise once the link works.

## What is most likely to go wrong

Written down now, so that a later failure is recognised rather than rediscovered:

* **The app may not be able to hand the descriptor over by number.** Clearing
  `FD_CLOEXEC` is necessary but may not be sufficient: Java's process spawn is
  not `posix_spawn` with an fd map, and the runtime has historically closed
  non-standard descriptors in the child before `exec`. Whether it does on this
  device is unverified and is the single cheapest thing to test first -- have
  umusb print `fstat` of the number it was given. If the descriptor does not
  arrive, every ioctl fails with `EBADF`, and the fix is to pass the descriptor
  itself rather than its number: a `LocalSocket` in the abstract namespace with
  `setFileDescriptorsForSend()`, which is `SCM_RIGHTS` under another name and
  needs no filesystem path, so the SELinux denial that blocks passt's `-s` mode
  (doc/90-networking.md) does not apply.
* **Latency.** Every URB is a round trip through vhci, a TCP connection, passt's
  userspace stack, umusb and usbfs. A guest syscall already costs 2.0 us in
  seccomp mode (doc/80-performance.md); a URB is going to cost a great deal more
  than that, and 802.11ac throughput is not the thing to expect first. Whether it
  is enough for association and a usable link is exactly what has to be measured.
* **The adapter's own speed.** The RTL8811AU is a USB 2.0 part, so `high` is the
  right default; if it lands on a super-speed hub port with a high-speed
  attachment, see the port/speed rule above.
* **Unplugging.** Killing umusb drops the TCP connection; vhci treats that as the
  device going away and tears it down, which the guest sees as an unplug. That is
  the intended behaviour, but it means a crashed helper looks exactly like
  somebody pulling the dongle out.
